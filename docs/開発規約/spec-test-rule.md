# テスト規約（spec-test-rule）

> 本プロジェクトのテスト（単体・結合）の階層、ディレクトリ、文書命名、ID 規則、テスト名、テストデータの原則を定める。AI がテスト仕様書・テストコード・テストレポートを生成する際は、本ファイルを [`spec-naming-rule.md`](spec-naming-rule.md)、[`spec-file-naming-rule.md`](spec-file-naming-rule.md) および各層の coding-rule と同時にプロンプトへ含めること。
> 本ファイルは「詳細設計 §5.1 UT 用例一覧 → テスト」間のテスト層 SSOT であり、規則のみを定める。ツールの実行手順や環境固有の設定は対象外とする。

---

## 1. 適用範囲

**適用対象**：バックエンド（Spring Boot）・フロントエンド（React）の単体テスト、API 結合テスト、画面結合テストの仕様書・コード・結果レポート、および詳細設計 §5.1 の UT 用例一覧。

**対象外**：システムテスト（§11 未決事項を参照）、性能・負荷試験、テスト環境のインフラ構築手順。

---

## 2. テスト階層

| 階層 | 工程略号 | 粒度 | 被テスト対象 | 外部依存の扱い |
|---|---|---|---|---|
| 単体テスト（バックエンド） | UT | クラス／メソッド単位 | `common`／`infrastructure` の共通基盤クラス、および各機能の ServiceImpl／Controller／Converter | §2.1 の L1〜L3 に従う |
| 単体テスト（フロントエンド） | UT | 関数／フック／コンポーネント単位 | 純粋関数（`src/api/` 等）、カスタムフック、プレゼンテーショナルなコンポーネント | ネットワークはモックしない（呼び出し先を差し替える） |
| API 結合テスト | IT | operationId 単位 | デプロイ済みの API 入口（Gateway）をブラックボックスで呼ぶ | 実システム・実 DB を使用。被テストコードに依存しない |
| 画面結合テスト | IT | 画面（SCR）単位 | コンポーネント木・状態・ルーティング・API 配線の協調 | ネットワーク層のみモック。Context／子コンポーネント／ルーターは実物 |

> 工程略号は `spec-file-naming-rule.md` §3 の体系 B（V 字工程コード）に従う。

<!-- rule: test.layers-l1-l2-l3 -->
### 2.1 バックエンドのテスト層（L1／L2／L3）

詳細設計 §5.1 の「推奨層」列はこの層を指す。

| 層 | 名称 | 方式 | 検証対象 | 基盤依存 | クラス名接尾辞 |
|----|------|------|---------|---------|----------|
| L1 | 単体 | JUnit 5 + Mockito（Spring コンテキストを起動しない） | ServiceImpl の純ロジック（採番、状態遷移、列挙変換、マスキング、Converter 写像）、共通基盤クラス | なし（Mapper・外部コンポーネントをモック） | `Test` |
| L2 | Web スライス | `@WebMvcTest` + MockMvc + 模擬ユーザー | Controller のルーティング、Bean Validation（400）、`@PreAuthorize`（403）、`Result`／`ErrorResponse` 包絡の構造 | テスト用セキュリティ設定、Service をモック | `Test` |
| L3 | プロセス内結合 | `@SpringBootTest` + Testcontainers（PostgreSQL） | HTTP → Controller → Service → MyBatis → 実 DB の全経路、暗号化ラウンドトリップ、マスク出力 | 共有テスト基盤（基底クラス、コンテナ設定、固定 dev 暗号鍵、オフライン JWT 署名ヘルパ、副作用スタブ） | `IT` |

- L1／L2 は常に生成する。L3 は共有テスト基盤が整っている場合にのみ生成し、未整備の場合は L1／L2 のみ生成して未生成である旨を明記する。
- 接尾辞はランナーの束縛を兼ねる（§7）。

## 3. ディレクトリ規約

テスト関連の文書・成果物は、基本設計／詳細設計と同階層に置く。

```
単体テスト/
├── バックエンド/
│   ├── spec-<対象 kebab-case>-unittest-sd.md      単体テスト仕様書（テスト項目表）
│   └── report/spec-ut-be-testreport-<date>.md       結果判定レポート（直近 1 回分）
└── フロントエンド/
    ├── spec-<対象 kebab-case>-unittest-sd.md
    └── report/
        ├── spec-ut-fe-testreport-<date>.md
        └── junit-<対象>-<date>.xml                  JUnit XML（レポートのデータ源）

結合テスト/
├── API/
│   ├── README.md                                    利用手順（起動前提・実行方法・token 取得）
│   ├── 課題.md                                      契約と実装の乖離の集約
│   ├── 式様書/spec-it-<operationId>.md              テスト式様書（人手審査対象・正本）
│   ├── fixtures/{seed,request,expected}/            テストデータ（§8）
│   ├── it-api-runner/                               API テストコード（独立プロジェクト）
│   └── report/spec-it-testreport-<date>.md
└── フロントエンド/
    ├── README.md
    ├── 課題.md
    ├── 式様書/spec-it-fe-<SCR-id>.md
    └── report/spec-it-fe-testreport-<date>.md

詳細設計/<機能名>/
├── spec-<feature>-detail-sd.md                      §5.1 UT 用例一覧を含む
├── spec-<feature>-testlist.md                       テスト一覧（生成したテスト資産の静的記録）
└── spec-<feature>-testreport.md                     テストレポート（実行結果。実行ごとに更新）
```

**テストコードの配置**

| 種別 | 配置 | 命名 |
|------|------|------|
| バックエンド L1／L2／L3 | 被テストクラスと同一モジュールの `src/test/java`、パッケージも本体と同一 | `<対象クラス名>Test`／`<対象クラス名>IT` |
| バックエンド共有テスト基盤 | 各サービスモジュールの `src/test/java/…/support/`、`src/test/resources/application-test.yml` | — |
| フロントエンド単体 | 対象ファイルと同じディレクトリ直下の `__tests__/` | `<対象ファイル名>.test.ts`（コンポーネントは `.test.tsx`） |
| フロントエンド画面結合 | フロントエンドプロジェクトの `src/` 配下（ネットワークモックのハンドラ、フィクスチャ、テスト本体） | — |
| API 結合 | `結合テスト/API/it-api-runner/`（バックエンドの reactor に含めない独立プロジェクト） | `*IT` |

## 4. テスト文書の命名

命名は `spec-file-naming-rule.md` の構造に従う。テスト関連の接尾辞・名称は以下のとおり。

| 文書 | ファイル名 | 配置 |
|------|-----------|------|
| 単体テスト仕様書 | `spec-<対象>-unittest-sd.md` | `単体テスト/{バックエンド,フロントエンド}/` |
| 単体テスト結果レポート | `spec-ut-be-testreport-<date>.md`／`spec-ut-fe-testreport-<date>.md` | `単体テスト/*/report/` |
| API 結合テスト式様書 | `spec-it-<operationId>.md` | `結合テスト/API/式様書/` |
| 画面結合テスト式様書 | `spec-it-fe-<SCR-id>.md` | `結合テスト/フロントエンド/式様書/` |
| 結合テスト結果レポート | `spec-it-testreport-<date>.md`／`spec-it-fe-testreport-<date>.md` | `結合テスト/*/report/` |
| テスト一覧 | `spec-<feature>-testlist.md` | `詳細設計/<機能名>/` |
| テストレポート | `spec-<feature>-testreport.md` | `詳細設計/<機能名>/` |

- 単体テスト仕様書は、対象クラスが複数ある場合は関連クラスを 1 ファイルにまとめてよい（代表クラス名またはパッケージ末尾の単位で命名する）。
- 結果レポートは直近 1 回の実行を記録し、実行のたびに上書きする（履歴を積み上げない）。失敗・スキップも事実のまま記載し、隠さない。
- **テスト一覧とテストレポートの区別**：一覧は「生成したもの」（テストファイル、UT-ID ↔ 用例 ↔ テストメソッドの対応、ゲート結果。再生成時のみ更新）、レポートは「実行した結果」（実行ごとに更新）。

## 5. ID 規則

<!-- rule: test.ut-id-format -->
<!-- rule: test.it-id-format -->
| ID | 形式 | 採番単位 | 使用箇所 |
|----|------|---------|---------|
| UT-ID | `UT-<FEATURE>-NNN` | 機能（`<FEATURE>` は機能 slug の英大文字表記）内の 3 桁連番 | 詳細設計 §5.1、テストメソッドの `@DisplayName`、§5 追跡マトリクス、テスト一覧・レポート |
| IT-ID（API） | `IT-<operationId>-NNN` | operationId 内の 3 桁連番 | 式様書のケース、`@DisplayName`、レポート |
| IT-ID（画面） | `IT-<SCR-id>-NNN` | 画面 ID 内の 3 桁連番 | 式様書のケース、テスト名（`it(...)`）の先頭、レポート |

- 1 ケース ＝ 1 つの ID ＝ 1 つのテストメソッド（`it(...)`）。
<!-- rule: test.ut-cases-single-source -->
- UT-ID の用例集合は詳細設計 §5.1 が唯一の源泉である。テスト工程で用例を追加・発明しない。不足を発見した場合は詳細設計へ差し戻す。
- IT のケース集合は契約（API 結合：`spec-07-api-list.yaml`／`spec-06-db-physical.yaml`／`spec-09-message-list.yaml`／`spec-03-auth-ui.md`、画面結合：画面のイベント・バリデーション設計）から導出する。契約が未定義の分岐は創作せず、式様書または課題一覧に記録して上流へ報告する。

## 6. テスト名と `@DisplayName`

<!-- rule: test.displayname-id-first -->
- **機能に紐付くバックエンドテスト（L1〜L3）**：すべての `@Test` に `@DisplayName("UT-<FEATURE>-NNN <条件→期待>")` を付与する。**ID を先頭に置くことは必須**であり、JUnit XML の `<testcase name>` から UT-ID を逆引きして要件単位の通過マトリクスを作るための前提となる。メソッド名は「条件_期待」が分かる英語 camelCase とする。
- **API 結合テスト**：`@DisplayName("IT-<operationId>-NNN <条件→期待>")`（必須）。
- **画面結合テスト**：`it('IT-<SCR-id>-NNN <条件→期待>', …)` のようにテスト名の先頭に IT-ID を含める（必須）。
- **機能に紐付かない共通基盤クラスのバックエンド単体テスト**：UT-ID は不要。`@DisplayName` に日本語の一言説明を付ける。
- **フロントエンド単体テスト**：`it(...)` の説明文でケースを識別する。画面文言そのものではなく、i18n キーまたは `t()` 呼び出し引数を検証する（多言語対応を壊さない）。
- 各テストメソッドは有効なアサーションを最低 1 つ持つ。

## 7. 実行とレポート

- **ランナーの束縛**：`*Test` は surefire（`test` フェーズ）、`*IT` は failsafe（`integration-test`／`verify` フェーズ）で実行する。対象モジュールに failsafe を設定しないと `*IT` が `mvn test` で実行されず、静かに漏れる。全層の実行は `mvn verify` とする。
- **JUnit XML に ID を載せる**：surefire・failsafe の双方で `statelessTestsetReporter`（`JUnit5Xml30StatelessReporter`）の `usePhrasedTestCaseMethodName=true` を設定し、`<testcase name>` が `@DisplayName` になるようにする。
- **レポートのデータ源は JUnit XML**（バックエンドは `target/surefire-reports/`、`target/failsafe-reports/`。フロントエンドは vitest の junit reporter 出力）であり、コンソール出力ではない。残存した古いレポート（stale）は無視する。
- レポートは「元情報／総覧／層別・ファイル別結果／ID 結果マトリクス／失敗詳細／結論と上流 TODO」を含み、生成した（または対象となった）テストファイルの一覧を必ず記載する。
- 環境が未起動で実行できない場合は結果を作らず、「実行待ち（NOT RUN）」と明記して起動方法を示す。

## 8. テストデータと種子の原則

本節は業務データを定めない。具体的なデータ値は各式様書・フィクスチャで、SSOT に基づいて定義する。

1. **既存の初期化スクリプトを再利用する**：テスト用の schema と種子は、データベース基本設計配下の初期化 SQL（schema／seed）を一次の供給元とする。テスト専用に schema を複製・再定義しない。不足分のみ冪等なフィクスチャ SQL を補う。
2. **API 結合テストの「mock」はテストデータを意味する**：独立した mock サーバや外部副作用のスタブではない。構成は ① 事前 DB シード／フィクスチャ、② リクエスト例、③ 期待レスポンス断片（messageId、主要項目、マスク期待値）の 3 点で、`fixtures/{seed,request,expected}/` に置く。
3. **冪等・再実行可能・後始末付き**：シードは再実行でき、teardown を伴う。共有 DB を叩く結合テストでは、アサーションを意味的・包含的にする（例：件数は `>=`、条件を満たす行のみであることの確認）。厳密な件数が必要な場合は専用フィクスチャ＋teardown とし、隔離方針を式様書に明記する。
4. **暗号化カラムは実暗号文**：復号を伴うケースのシードは、実行サービスと同一の鍵で暗号化した実暗号文を用いる。プレースホルダ文字列に対するアサーションは行わない。
5. **鍵・秘密情報の置き場**：テスト用の固定暗号鍵と JWT の署名設定は `src/test`（テスト用プロファイル）にのみ置く。`src/main` にハードコードしない。種子の暗号化に使う鍵とテスト実行時の鍵は同一値とし、不一致による復号失敗を防ぐ。
6. **認証トークンはオフライン署名**：L3 および API 結合テストは、本番と同一の署名設定で JWT をテスト側で署名して使う（ログインフロー・メール・ワンタイム資格情報に依存しない）。L2 は模擬ユーザー（ロール指定）で `@PreAuthorize` を検証する。
7. **副作用の隔離**：メール送信・サービス間呼び出し・ファイルストレージ・外部ストア等の外部副作用は、L1／L2 ではモック、L3 ではスタブ Bean で置換し、実際の外部リクエストを送らない。
<!-- rule: test.expected-from-ssot -->
8. **期待値の根拠は SSOT**：messageId ← `spec-09-message-list.yaml`、HTTP 状態 ← 例外型ごとの固定マッピング、レスポンス構造 ← 共通レスポンス型と `spec-07-api-list.yaml`、マスク ← `spec-03-auth-ui.md`、入力境界 ← `spec-07-api-list.yaml`。実装の挙動をそのまま正解にしない。

## 9. 品質ルール

- **禁止事項**：空のアサーション、恒真アサーション、コメントアウトされたテスト、理由のない `@Disabled`、ゲートを通すためだけの空実装。
- **契約と実装の乖離**：契約（SSOT）が正本であり、実装は正解ではない。乖離はテスト層で取り繕わず、テストを失敗（RED）のまま上流へ報告するか、式様書・課題一覧に記録して人手で裁定する。実装コードの不具合をテストで発見しても、テスト作成の依頼の範囲で実装を変更しない。
- **セキュリティ上の欠陥を現状の正しい挙動として固定しない**：期待値には「あるべき安全な挙動」を書き、実装が未対応である旨を備考に明記して報告する。
- **既存テストの保護**：人手で作成・修正されたテストは盲目的に上書きしない（更新時は差分を取り、新規／更新／スキップを区別する）。
- **人手審査門**：結合テストは、式様書の審査状態が「承認済み」になってから、テストデータ・テストコードを生成する。
- **テスト対象の優先度（フロントエンド単体）**：純粋関数 → カスタムフック → プレゼンテーショナルなコンポーネントの順に優先する。画面本体や重量級依存を合成するだけのコンテナは原則対象外とし、対象外とする理由（ライブラリ内部動作の検証になる／自コードのロジックが無い）を 1 文で明記する。依存の種類（router、Context、i18n）の有無そのものは対象外の理由にしない。
- **モックの範囲**：フロントエンドは Context をモジュールごとモックせず、テスト用の値を持つ Provider でラップする。i18n は `t()` をキー返しに単純化する。
- **改行・文字コード**：`開発規約/spec-backend-coding-rule.md` §12 に従う。

## 10. 他の規約との関係

| 規約 | 関係 |
|------|------|
| `spec-backend-coding-rule.md` | バックエンドのテストは同書の層構成・命名・例外マッピング（例外型 → HTTP 状態）・マスキングの規則に従う。テスト層の規則は本規約を正とし、実装規則は同書を正とする |
| `spec-frontend-coding-rule.md` | フロントエンドのテストは同書のコンポーネント接尾辞・ディレクトリ・状態管理（Context）・i18n・Union Type の規則に従う。同書に定めのないテスト固有の規則は本規約を正とする |
| `spec-naming-rule.md` | クラス・メソッド・operationId・画面 ID の命名を正とする。テスト ID は本規約 §5 |

| `spec-codegen-map-rule.md` | コード生成の一頁索引。テスト生成（用例一覧 → テストコード）の入力は詳細設計 §5.1 |
| 詳細設計テンプレート（`詳細設計/spec-detail-temp.md`） | §5.1 UT 用例一覧がバックエンド単体テストの用例の唯一の源泉。§6.1 D11 でカバレッジを検査する |

**優先順位（競合時）**：`spec-naming-rule.md` ／ `spec-database-rule.md`（承認済み規約）> 各層 coding-rule > 本規約 > 詳細設計 > 各 yaml。競合は上位を正として書き戻す。

## 11. 未決事項

- システムテスト（ST）の定義・ディレクトリ・文書名・ID 規則（参照元のテスト系 skill に ST 工程の規則が無いため未定義）。
- フロントエンド単体テスト仕様書の項目 ID の採番規則（UT-ID はバックエンド用例にのみ規定され、フロントエンド仕様書は「実装状況」列で項目管理されている）。
- フロントエンド単体テストの実行環境（`happy-dom`／`jsdom`）の既定値（プロジェクトの実設定に従う運用で、固定規則が無い）。
- 結合テスト式様書名（`spec-it-<operationId>.md` の camelCase 部分）と `spec-file-naming-rule.md` §2 の「すべて小文字」規則の整合。
- 結合テスト式様書・結果レポートの接尾辞（`-integrationtest-sd` 等）の統一方針（現行は §4 の名称で運用）。
- 詳細設計ディレクトリの `-testlist`／`-testreport` と `単体テスト／結合テスト` 配下レポートの使い分け・重複記録の扱い。
- フロントエンドの機能単位の UT 用例一覧（§5.1 のフロントエンド版）の有無。
- 画面結合テストの ID に使う画面 ID の表記（`SCR-<n>` か機能別接頭辞付きか）。
- L3 のデータベース（Testcontainers か常設 DB か）、シード戦略、CI での L3 実行可否（テスト基盤構築時の決定事項で、規約化されていない）。
