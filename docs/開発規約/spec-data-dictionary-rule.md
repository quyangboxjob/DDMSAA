## 使用規則

- AI が DB スキーマを生成する際は、以下の文書を必ず併せて参照すること。
  1. DB開発規約（命名規約）
  2. 本ファイル（データ辞書規範：基礎型定義 + 規則 + 共通項目の層間対照）
  3. プロジェクトデータ辞書（T07列挙型 + 列定義 + Principle 3 ホワイトリスト）
- 本辞書は**第1部：基礎型定義**、**第2部：列定義**、**第3部：Universal Field Name Reference** の3層構造を採る
- 列定義層のすべての列は第1部の基礎型を参照しなければならず、列定義層での制約の追加は禁止する
- DB スキーマ生成時、すべての列はプロジェクトデータ辞書の列定義を参照しなければならず、辞書に存在しない列は使用禁止とする
- 列を追加する際は、まず第1部で基礎型を確認または新設し、次に第2部で列定義を登録し、最後にスキーマで使用すること
- T07列挙型の属性名はアプリケーション層（Enum クラスなど）が保持するため、JOIN による表示名の取得は不要である
<!-- rule: enum.code-table-rows -->
- T07列挙型は、DDL 内で列挙型ごとのコードテーブルと、それを参照する外部キーとして生成する（コードテーブルの規約は `spec-database-rule.md` §4.1-CODE）。コードテーブルの行（コード・英語名）は T07 の定義と一致させる

**`description` 列の命名規則：**

- 1テーブルに説明項目が1つのみの場合は、素の `description` を使用する
- 1テーブルに複数の説明次元が存在する場合は、すべての説明項目に主体プレフィックスを付けなければならず（例：`summary_description` と `traffic_description`）、孤立した素の `description` を残すことは禁止する
- 設計段階で複数の説明項目の存在が予見される場合は、最初から `{domain}_description` 形式を使用し、素の `description` は使用しない
- 後続の要件で2つ目の説明項目を追加する場合、既存の `description` はマイグレーションにより `{domain}_description` へリネームしなければならない

**DDL コメントの言語規則：**

- `COMMENT ON COLUMN` / `COMMENT ON TABLE` は**日本語で統一**する（本システムは日本の業務システムであり、論理名は要件定義を正とする。v1.6.0 改訂履歴を参照）
- コメント内容は業務論理名とする（実装詳細は書かない）。**すべてのテーブル、すべての列にコメントを付与し、かつ `CREATE TABLE` と一緒にテーブル作成 DDL 内で記述しなければならない——コメントがない場合はテーブル作成が未完了とみなす。**
- **形式**：テーブルは `COMMENT ON TABLE {テーブル名} IS '{日本語論理名}';`、列は `COMMENT ON COLUMN {テーブル名}.{列名} IS '{日本語論理名}';`。値は純粋な日本語論理名とする。`'...'` と `E'...'`（エスケープ文字列）は等価であり、エスケープが不要な場合は `'...'` に統一する。
- **例**：`COMMENT ON TABLE users IS 'ユーザー基本情報';` / `COMMENT ON COLUMN users.user_id IS 'ユーザーID';`

| 禁止（英語/中国語） | 許可（日本語論理名） |
|---|---|
| `Order status` | `注文ステータス` |
| `User ID` | `ユーザーID` |
| `Customer name` | `顧客名` |

<!-- rule: enum.change-order -->
**T07列挙型の変更規則（本番運用で安全な順序）：**

値域の**拡大**（列挙値の追加）時は、以下の順序で実施しなければならない。

| ステップ | 操作 | 説明 |
|---|---|---|
| 1 | プロジェクトデータ辞書の T07 定義を更新 | 唯一の定義元であり、必ず最初に行う |
| 2 | マイグレーションスクリプトでコードテーブルに行を追加 | 先に DB の許容範囲を広げ、アプリケーションのリリース後に新しい値の書き込みが DB に拒否されることを防ぐ |
| 3 | 辞書に基づきアプリケーション層の Enum クラスを更新してデプロイ | DB の準備が整ってからアプリケーションコードをリリースする |

値域の**縮小**（列挙値の廃止）時は、以下の順序で実施しなければならない。

| ステップ | 操作 | 説明 |
|---|---|---|
| 1 | プロジェクトデータ辞書の T07 定義を更新（廃止を明記） | 唯一の定義元であり、必ず最初に行う |
| 2 | アプリケーション層の Enum クラスを更新してデプロイ（廃止値の書き込みを停止） | 先に廃止値の発生を止める |
| 3 | 履歴データ中の廃止値をクリーンアップ | DB に廃止値が残っていないことを確認する |
| 4 | マイグレーションスクリプトでコードテーブルから廃止値の行を削除 | 履歴データのクリーンアップ完了後に値域を絞り込む |

上記の順序を逆にすることを禁止する。辞書は常に先行しなければならない。

# 第1部：基礎型定義

> すべての列定義は、ここで定義した基礎型を参照する。
> 基礎型は DB 型・制約・取りうる値の範囲の唯一の定義元（Single Source of Truth）である。
> 基礎型を変更すると、その基礎型を参照するすべての列定義が自動的に影響を受ける。
> 基礎型定義は汎用規範であり、プロジェクトの業務内容を含まず、全プロジェクトで共用する。

---

## T01 整数・識別子型グループ

- 外部キー参照には `必須外部キー型` / `任意外部キー型`（文字列型）を使用しなければならず、外部キー列に `必須整数型` や `任意整数型` を使用することを禁止する
- 主キーに用いる基礎型の選択（既定の `必須ID型`、代替の `必須連番型`）と採番は `開発規約/spec-database-rule.md` §4.1 に従う
- あるテーブルが `必須連番型`(BIGINT) の数値主キーを選択した場合、その外部キー列は BIGINT を使用し、当該列定義の説明欄にその旨を明記する

| 型名 | DB型 | 制約 | 用途説明 |
|---|---|---|---|
| `必須整数型` | INTEGER または NUMERIC | NOT NULL DEFAULT 0 | 件数、数量、順序などの必須の整数値。どちらも可（INTEGER は 4 バイトで約 ±21 億、NUMERIC は任意精度）。外部キーへの使用は禁止 |
| `任意整数型` | INTEGER または NUMERIC | NULL | 省略可能な整数値。どちらも可。外部キーへの使用は禁止 |
| `必須ID型` | VARCHAR(10) | NOT NULL | 文字列主キー専用。採番は `開発規約/spec-database-rule.md` §4.1-SEQ に従う |
| `必須連番型` | BIGINT | NOT NULL GENERATED ALWAYS AS IDENTITY | （代替）数値自動採番の主キー。使用条件は `開発規約/spec-database-rule.md` §4.1 に従う |
| `必須外部キー型` | VARCHAR(10) | NOT NULL | 文字列の外部キー参照。型は参照先テーブルの `必須ID型` と一致していなければならない |
| `任意外部キー型` | VARCHAR(10) | NULL | 省略可能な文字列の外部キー参照 |
| `必須監査者型` | VARCHAR(10) | NOT NULL DEFAULT 'SYSTEM' | 監査項目 created_by/updated_by 専用。操作者のユーザーIDを格納。システム/初期データは 'SYSTEM' を使用 |

## T06 論理型グループ

> 型名中の `フラグ` はカタカナであり、他の型名の漢字表記とは様式が異なるが、確立済みの命名として踏襲する。型名体系では、日本語の漢字とカタカナの併存を許容する。

| 型名 | DB型 | 制約 | 用途説明 |
|---|---|---|---|
| `フラグ型_デフォルト偽` | BOOLEAN | NOT NULL DEFAULT FALSE | 二値フラグ、デフォルト FALSE |
| `フラグ型_デフォルト真` | BOOLEAN | NOT NULL DEFAULT TRUE | 二値フラグ、デフォルト TRUE。**警告**：`ALTER TABLE ADD COLUMN` を実行すると、既存行は自動的に TRUE となる。消極的デフォルトの原則（Negative Default Principle）に基づき、原則として `フラグ型_デフォルト偽` を優先使用し、列名の反転（例：`is_available` → `is_restricted`）で代替する |

## T07 列挙型グループ（規則説明）

> T07 の具体的な列挙型定義（業務内容）は、各プロジェクトの `data-dictionary-{project}.md` に記載する。
> 本節では T07 の共通規則のみを定義する。

### T07共通規則

- DB 実装は列挙型ごとのコードテーブル + 外部キーとする（`spec-database-rule.md` §4.1-CODE）
- 列定義層の DB 型は `INT NOT NULL`（必須）または `INT NULL`（省略可）とする
<!-- rule: enum.value-source-t07 -->
- 取りうる値の範囲（Enum Values）は、プロジェクトデータ辞書の T07 定義を唯一の定義元とする
- 属性名の表示はアプリケーション層の Enum クラスが担い、JOIN は不要である
<!-- rule: enum.category-code-rule -->
- `category_code` は列挙型グループの一意な番号であり、列挙型をまたいで管理する際にカテゴリを区別するために用いる。プロジェクトデータ辞書内で一意であることを要し、追加時は現在の最大番号+1とする。廃止済みの番号は再利用不可とし、廃止時は番号を保持したまま定義箇所に「廃止済み」と明記する
- T07 の値を変更する際は、上記「T07列挙型の変更規則」の順序で実施しなければならない

### T07定義形式規範

各プロジェクトのデータ辞書では、T07 列挙型を以下の形式で定義しなければならない。

```markdown
### {型名} ({enum_type_name_snake_case})

- **対応 category_code**: {数字、全プロジェクトで一意、連続加算}
- **DB実装**: `INT NOT NULL` または `INT NULL`
- **コードテーブル**: `{enum_type_name_snake_case}_codes`（下表の行を保持する）

| 属性コード | 属性名 | 英語名 |
|---|---|---|
| {数字} | {名称} | {english_name} |
```

# 第2部：列定義（規則説明）

> 第2部の具体的な列定義（業務内容）は、各プロジェクトの `data-dictionary-{project}.md` に記載する。
> 本節では列定義の共通規則と形式規範のみを定義する。

### 列定義共通規則

- すべての列は第1部の基礎型を参照し、列定義層での制約の追加・変更を禁止する
- 英語列名のアルファベット順で統一管理する。列を追加する際は順序を維持すること
- DB スキーマ生成時は、プロジェクトデータ辞書の列定義を唯一の参照元とする
- T07列挙型を参照する列は、説明欄に「参照: {型名}」の形式で明記すること
- 列名の長さは `spec-database-rule.md` §2.4 の30文字制限に従う

### 列定義形式規範

各プロジェクトのデータ辞書では、列定義を以下の形式（「必須/任意」と「デフォルト値」の列を含む）で定義しなければならない。

```markdown
| 業務用語 | 英語列名 | 参照基礎型 | 必須/任意 | デフォルト値 | 説明 |
|---|---|---|---|---|---|
| {業務用語} | `{column_name}` | `{基礎型名}` | 必須/任意 | {デフォルト値または「-」} | {説明。T07を参照する場合は「参照: {型名}」と記載} |
```

- 「必須/任意」列は基礎型名のプレフィックスと一致させる：`必須` で始まる基礎型 → 必須、`任意` で始まる基礎型 → 任意
- 「デフォルト値」列には業務上のデフォルト値（例：`0`、`1`、`FALSE`）を明記しなければならない。デフォルト値がない場合は `-` を記入し、空欄にしてはならない

### 必ず含める共通列

以下の列は、すべてのデータテーブルに存在しなければならず、プロジェクトの列定義で重複登録する必要はない。

| 業務用語 | 英語列名 | 参照基礎型 | 必須/任意 | デフォルト値 | 説明 |
|---|---|---|---|---|---|
| 主キー | `id` | `必須ID型` | 必須 | 採番関数 | 全テーブル共通の主キー。採番は `開発規約/spec-database-rule.md` §4.1-SEQ に従う |
| 作成日時 | `created_at` | `作成日時型` | 必須 | CURRENT_TIMESTAMP | レコード作成日時 |
| 作成者 | `created_by` | `必須監査者型` | 必須 | 'SYSTEM' | 作成者のユーザーID。システム/初期データは 'SYSTEM' を使用 |
| 更新日時 | `updated_at` | `更新日時型` | 必須 | CURRENT_TIMESTAMP | レコード更新日時（トリガーの登録が必須） |
| 更新者 | `updated_by` | `必須監査者型` | 必須 | 'SYSTEM' | 更新者のユーザーID。システム/初期データは 'SYSTEM' を使用 |
| 削除日時 | `deleted_at` | `論理削除日時型` | 任意 | NULL | 論理削除日時。NULL = 有効 |

> **主キーの例外**：1:1 / 0..1 の子テーブル（共有主キー）・設定/参照系の master（自然キー）・`users`（`user_id`）では `id` を省略できる。適用条件と採番の扱いは `開発規約/spec-database-rule.md` §4.1 に従う。

# 第3部：Universal Field Name Reference

> 本節は、すべてのテーブルに共通する項目の各層における名称対照規範を定義し、全プロジェクト共用の基準とする。
> 業務項目の層間対照は、プロジェクトデータ辞書の Principle 3 ホワイトリストで管理し、本節には登録しない。

## 共通項目の層間対照表

| 業務概念 | DB | Backend Entity | API JSON | Frontend |
|---|---|---|---|---|
| 内部主キー（二重 ID 方式・任意） | `id` | `id`（Long） | 対外非公開 | 存在しない |
| 対外一意識別子（二重 ID 方式・任意） | `external_id` | `externalId`（UUID） | `id`（※タイプA変換） | `id: string` |
| 作成日時 | `created_at` | `createdAt` | `createdAt` | `createdAt: string` |
| 作成者 | `created_by` | `createdBy` | `createdBy` | `createdBy: string` |
| 更新日時 | `updated_at` | `updatedAt` | `updatedAt` | `updatedAt: string` |
| 更新者 | `updated_by` | `updatedBy` | `updatedBy` | `updatedBy: string` |
| 論理削除日時 | `deleted_at` | `deletedAt` | 対外非公開 | 存在しない |

> **採番主キーのプロジェクト（本プロジェクトが該当する類型）**：`id`(Long)/`external_id` の二重 ID を使用せず、業務主キーは `VARCHAR(10)` の採番を採用し、そのまま対外公開する（DB の `id`/`user_id` → API/Frontend で同名）。上表の `id`(Long)+`external_id` の2行は二重 ID 方式の汎用的な例示にすぎず、この類型のプロジェクトでは有効化しない（下記の説明および DBQ-08 を参照）。

## 時間項目の取り扱い規則

- **DB**：`TIMESTAMPTZ` 型（タイムゾーンの扱いは `spec-database-rule.md` §5.1 に従う）
- **Backend**：`OffsetDateTime`
- **API JSON**：日時の表記は `基本設計/共通/spec-07-api-list-ui.md` に従う
- **Frontend**：`string` 型で受け取る（表示書式は `基本設計/共通/spec-12-screen-common-ui.md` に従う）

## 共通項目の説明

- `id`（内部主キー）と `deleted_at`（論理削除日時）は API および Frontend に対して非公開とする
- 対外一意識別子 `external_id` は API JSON および Frontend では `id` として公開される。これはタイプA変換（意味境界の絞り込み）であり、変換登録はプロジェクトデータ辞書の Principle 3 ホワイトリストを唯一の参照元とする
- ⚠ **本プロジェクトは `external_id` / 内部 Long の二重 ID を採用しない**：業務主キーは `VARCHAR(10)` の業務採番を採用する（users=`user_id`、ユーザーIDをそのまま対外公開）。本節の `external_id`/`id(Long)` は汎用規約の例示であり、二重 ID 方式は**有効化しない**（DBQ-08 解決済み）。
- 全テーブルで実際に作成が必須となる共通列は、第2部「必ず含める共通列」を正とする（6 列：`id` / `created_at` / `created_by` / `updated_at` / `updated_by` / `deleted_at`。採番主キーのプロジェクトは `external_id` を含まない）。本節はこれらの項目の**層間命名対照**のみを規定するものであり、プロジェクトデータ辞書の列定義で重複登録する必要はない
