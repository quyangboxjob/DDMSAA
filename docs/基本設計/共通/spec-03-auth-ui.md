# 03 認証・認可設計

<!-- rule: auth.access-scope -->

## 1. 採用方針

DDMSAA は、`login_id` とパスワードによるログインを採用する。認証後はランダムなサーバー側セッションを `HttpOnly`・`Secure`・`SameSite=Lax` Cookie `DDMSAA_SESSION` として発行する。メールは注文・承認・取消しの通知にだけ使用し、認証用リンクは使用しない。

- パスワードは BCrypt ハッシュだけを保存し、平文・復号可能な暗号文を保存しない。
- 同一 `login_id` の連続失敗が 5 回に達したら 30 分ロックする。ログイン失敗時の応答は常に同じにし、アカウントの存在を開示しない。
- セッションは 8 時間で失効する。ログアウト、無効化、パスワード変更では失効させる。
- Cookie を使う変更系 API は CSRF トークンを検証する。HTTPS は本番必須である。

## 2. ロールとデータ範囲

| ロール | 利用者 | 操作範囲 |
|---|---|---|
| `ADMIN` | システム管理者 | 全顧客・全注文。ユーザー、顧客、商品、承認経路、監査、帳票を管理できる |
| `EMPLOYEE` | 営業・事務担当 | `employee_customer_assignments` で有効な担当顧客だけを参照・登録・更新・申請できる |
| `CUSTOMER` | 顧客の閲覧アカウント | 自身の `customer_id` の注文・承認結果・顧客公開かつ安全な添付・帳票だけを参照できる |

`CUSTOMER` は、注文作成、変更、取消し、承認、商品・顧客・ユーザー管理、添付アップロード/削除、CSV 出力を行えない。`EMPLOYEE` は担当外顧客を URL やリクエスト値で指定しても参照・操作できない。すべての API と SQL はサーバー側でこの範囲を強制する。

## 3. 権限マトリクス

| 機能 | ADMIN | EMPLOYEE | CUSTOMER |
|---|:---:|:---:|:---:|
| ログイン/自分の情報 | ○ | ○ | ○ |
| ユーザー・顧客・商品管理 | ○ | × | × |
| 担当顧客の注文作成・編集・申請 | ○ | ○ | × |
| 注文取消し | ○ | 作成/担当分のみ | × |
| 承認・差戻し | ○ | × | × |
| 添付アップロード/削除 | ○ | 担当注文のみ | × |
| 添付参照 | ○ | 担当注文のみ | 自顧客かつ `CUSTOMER` 公開・`SAFE` のみ |
| PDF 帳票 | ○ | 担当顧客分のみ | 自顧客分のみ |
| CSV 集計/出力 | ○ | 担当顧客分のみ | × |
| 監査ログ・送信ログ | ○ | × | × |

## 4. 実装境界

1. Controller は認証済み主体だけを `UserContext` として受け取る。
2. Service がロール、顧客所属、担当割当、注文状態を検証する。
3. Repository は Service から渡された `customer_id` / `sales_user_id` のスコープ以外を検索しない。
4. 権限拒否は `403`、存在しないもの又は範囲外のものは情報漏えいを避け `404` を返す。
5. 認証・認可・状態変更・添付ダウンロード・CSV 作成は `audit_logs` に記録する。
