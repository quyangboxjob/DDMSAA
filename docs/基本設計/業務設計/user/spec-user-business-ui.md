## 2. 目的・範囲

本モジュールは、利用者のログイン、ログアウト、役割、所属顧客、有効状態および認可に必要な情報を管理する。初版の役割は「システム管理者」「一般社員」「顧客」の 3 種類に固定する。

## 3. 権限方針

| 操作 | システム管理者 | 一般社員 | 顧客 |
| --- | --- | --- | --- |
| 利用者の登録・編集・無効化 | ○ | × | × |
| 商品・顧客マスタの管理 | ○ | × | × |
| 担当注文の登録・更新 | ○ | ○ | × |
| 自社注文の閲覧 | ○ | 担当分を閲覧 | ○ |
| 承認操作 | ○ | 承認者に指定された場合のみ | × |
| 監査ログの閲覧 | ○ | × | × |

顧客役割の利用者には `customer_id` を必須とし、注文・添付取得 API は常に当該 `customer_id` でデータを絞り込む。画面の非表示だけで制御してはならない。

## 4. 画面

| 画面 ID | 画面名 | 主な利用者 | 主な機能 |
| --- | --- | --- | --- |
| SCR-USR-01 | ログイン | 全利用者 | ユーザー名またはメールアドレスとパスワードで認証する。 |
| SCR-USR-02 | 利用者一覧 | 管理者 | 検索、有効/無効の確認、新規登録画面への遷移。 |
| SCR-USR-03 | 利用者登録・編集 | 管理者 | 氏名、メール、役割、所属顧客、有効状態を設定する。 |
| SCR-USR-04 | 自分のプロフィール | 全利用者 | 氏名・メールの表示、パスワード変更への導線。 |

## 5. 主要処理

1. 管理者が利用者を登録する。顧客役割を選択した場合は所属顧客の選択を必須とする。
2. 利用者はログインする。無効利用者または認証失敗時はログインを許可しない。
3. 認証後、サーバーは利用者 ID、役割、所属顧客、担当範囲をセッションまたはトークンに関連付ける。
4. 各 API は認可処理を実行する。顧客による他社データの参照要求は 403 または 404 とし、情報を返さない。
5. 管理者が利用者を無効化した場合、以降の新規ログインを拒否し、必要に応じて既存セッションを失効させる。

## 6. 主なデータ

| エンティティ | 主な項目 | 制約 |
| --- | --- | --- |
| users | user_id, login_id, display_name, email, role, customer_id, status | login_id と email は一意。顧客は customer_id 必須。 |
| roles | role_code, role_name | 初版は ADMIN / EMPLOYEE / CUSTOMER。 |
| user_customer_assignments | user_id, customer_id | 顧客利用者の所属および社員担当範囲の拡張用。 |
| audit_logs | actor_user_id, action, target_type, target_id, occurred_at, summary | 更新・権限変更・ログイン失敗を記録する。 |

## 7. API 概要

| メソッド | パス | 権限 | 内容 |
| --- | --- | --- | --- |
| POST | `/api/auth/login` | 未認証 | 認証してセッションを開始する。 |
| POST | `/api/auth/logout` | 認証済み | セッションを終了する。 |
| GET | `/api/users` | 管理者 | 利用者一覧を取得する。 |
| POST | `/api/users` | 管理者 | 利用者を登録する。 |
| PATCH | `/api/users/{userId}` | 管理者 | 利用者情報・有効状態を変更する。 |
| GET | `/api/me` | 認証済み | 自身の表示用情報・権限を取得する。 |

## 8. 入力・監査・セキュリティ

- パスワードは平文保存せず、強度要件を満たすハッシュだけを保存する。
- 連続ログイン失敗、権限変更、利用者登録・無効化を監査ログに記録する。
- セッションの有効期限とログアウト後の無効化を実装する。具体的な期限は運用設計で決定する。
