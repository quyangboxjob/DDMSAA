# 業務基本設計 — 承認管理

## 1. 初版の承認経路

初版は、注文金額にかかわらず ADMIN による 1 段承認とする。ADMIN が後から経路マスタを更新できるが、変更は新しい申請だけに適用する（BR-APR-001）。

## 2. 処理

1. ADMIN 又は担当 EMPLOYEE が DRAFT/RETURNED 注文を申請する。
2. システムは申請時検証（BR-ORD-010）を行い、有効な承認経路を注文にスナップショット保存し、状態を PENDING_APPROVAL にする。有効な ADMIN（申請者を除く）全員に通知する。
3. 申請者以外の有効な ADMIN の誰か 1 名が、承認又は理由付き差戻しを行う。処理した ADMIN を承認依頼に記録する。
4. 承認で APPROVED、差戻しで RETURNED に遷移する。
5. 操作履歴、状態履歴、通知ジョブ、監査ログを保存する。

## 3. 制約

- 承認者は特定しない。有効な ADMIN のうち申請者本人以外が承認・差戻しでき、申請者本人は自分の注文を承認・差戻しできない（`E0056`。BR-APR-002）。
- 2 名の ADMIN が同時に処理した場合は先に処理した結果を正とし、後の操作は `E0006` とする（BR-APR-005）。
- 有効な ADMIN が申請者 1 名だけのときは承認できない。運用で別の ADMIN を用意する。
- 差戻し理由は 1～500 文字必須（BR-APR-003）。
- 代理承認、多段承認、金額別経路は初版では実装しない。承認ルールの承認者ロールは ADMIN、承認段階は 1 に固定する。ただしテーブル構造は将来の追加を妨げない。
- 承認待ち中の注文は編集・取消し不可。
- CUSTOMER には承認履歴の操作種別と日時だけを見せ、操作者と理由は見せない（BR-APR-006）。
