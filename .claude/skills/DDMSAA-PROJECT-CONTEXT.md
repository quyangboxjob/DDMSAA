Read this file before resolving project paths or generating an artifact. The current repository is the only source of truth. All design documents live under `docs/`; do not edit them from a skill unless the skill's task is to produce that document.

## Authority order (when sources conflict)

From `docs/開発規約/spec-generation-rule.md` §1 — higher wins:

1. Approved rules: `spec-naming-rule.md`, `spec-database-rule.md`
2. Layer coding rules: `spec-backend-coding-rule.md`, `spec-frontend-coding-rule.md` (and `spec-test-rule.md`, `spec-flyway-migration-rule.md`, `spec-sql-lint-rule.md`)
3. Feature detailed design (`docs/詳細設計/業務/<feature>/...`)
4. Machine-readable data sources (the `*.yaml` files below) — these are data sources/drafts and lose to the rules above

If a lower source contradicts a higher one, report it and follow the higher one. If two sources at the same level conflict, stop and report; do not choose an undocumented default. Known conflicts are listed at the end.

## Repository layout

- Backend root: `ddmsaa-backend/` — modules `api-gateway`, `auth-service`, `business-service-core`, `common`, `infrastructure`. Java packages `com.example.ddmsaa.{gateway|auth|core|common|infrastructure}`.
- Frontend root: `frontend/`, source `frontend/src/`. Layout (from `spec-frontend-coding-rule.md` §1), file names kebab-case:
  - `pages/<domain>/<feature>-page.tsx`
  - `components/<domain>/<feature>-<role>.tsx`
  - `types/<domain>.ts` (one file per domain)
  - `api/<domain>-api.ts` (one file per domain; function name = operationId)
  - `i18n/messages.ts`, `routes.tsx`
- Backend business code: `ddmsaa-backend/business-service-core/src/main/java/com/example/ddmsaa/core/<feature>/{controller,service,service/impl,mapper,entity,dto,convert}/`
- Mapper XML: `ddmsaa-backend/business-service-core/src/main/resources/mapper/<Feature>Mapper.xml`
- Flyway migrations: `ddmsaa-backend/infrastructure/src/main/resources/db/migration/`
- Initial DB SQL (generated by `spec-scaffold-db`): `docs/基本設計/データベース/setup/` — **does not exist yet**
- Feature business design: `docs/基本設計/業務設計/<feature>/spec-<feature>-business-ui.md` and `spec-<feature>-screen-ui.md` (`attachment` has no screen-ui; its screens are in `order`)
- Feature detailed design: `docs/詳細設計/業務/<feature>/spec-<feature>-detail-sd.md`
- Per-feature ledgers next to it: `spec-<feature>-filelist.md` (generated files), `spec-<feature>-flow.md` (flowchart), `spec-<feature>-testlist.md`, `spec-<feature>-testreport.md`; cross-feature issue list `docs/詳細設計/業務/spec-business-issue.md`

**Features** (replace the old numeric workflow ids): `user` (login, Magic Link, user admin — `/auth/**` is in `auth-service`, the rest in `business-service-core`), `customer`, `product`, `order`, `approval` (approval + notifications), `attachment`, `report`. Do not invent mappings from workflow numbers. Suggested dependency order for generation: user → customer → product → order → approval → attachment → report (verify against `spec-06` foreign keys before relying on it).

## Non-negotiable constraints

- Frontend: React 19, TypeScript strict, Vite, Ant Design, React Router, Context + Hooks, `react-i18next`. Dev server port 3000.
- Backend: Spring Boot 3.5.13, Java 21, Maven, MyBatis, MapStruct for Converters, PostgreSQL 16, Redis 7.
- Initial schema is created by the Docker init scripts; Flyway uses baseline `0`, initial data in `V1`, later schema changes from `V2+`.
- Authentication: passwordless Magic Link + JWT access token (60 min, no refresh). No password login, password hashes, refresh tokens, or lockout by failure count. JWT `issue(userId, role)`.
- Roles: `ADMIN`(1), `EMPLOYEE`(2), `CUSTOMER`(3). Authorization and data scope per operation come from `x-roles` in 07 and `spec-03-auth-ui.md`. Out-of-scope single resources return 404 (BR-AUTH-006).
- Protected APIs use `Authorization: Bearer <JWT>`. Ports: gateway `8080`, auth `8081`, business `8082`, frontend `3000`, host PostgreSQL `5434`.
- Data conventions: PK `VARCHAR(10)` (2-letter prefix + 8 digits via `next_business_id`; `users` use A/E/C + 4 digits); enums are INT + `*_codes` FK (T07), not CHECK; optimistic lock on `updated_at` (microsecond precision, conflict `E0051`, wrong state `E0006`); success is HTTP 200 + `Result`.
- **Cross-feature calls** go through 8 ports in `com.example.ddmsaa.core.shared.port` (formal definition: `docs/詳細設計/業務/order/spec-order-detail-sd.md` §1.1.1): `ApprovalRequestPort` (approval), `OrderStatePort` (order), `NotificationPort` (approval), `AuditLogPort` (user; `record` and `recordDenied`), `OrderAccessPort` (order), `DataScopePort` (customer), `CustomerLookupPort` (customer), `ProductLookupPort` (product). A feature never references another feature's Service or Mapper. Enums: `Role` in `common.enums`, all other T07 enums in `core.shared.enums`.
- **Errors**: service-layer 400 is `InvalidRequestException` (default `E0008`); `BusinessException` is always 409; malformed requests (bad enum, bad JSON, missing param/part) are 400 `E0008`; 413 is `PayloadTooLargeException`. `PERMISSION_DENIED` is recorded by `PermissionDeniedAuditListener` (403) and by the range check before it throws 404 (`AuditLogPort.recordDenied`, new transaction).
- **Batches** (spec-15): BAT-01 notification send, BAT-02 CSV, BAT-03 export expiry, BAT-04 attachment retention, BAT-05 attachment virus scan (a 1-minute poller; upload only stores `PENDING`). `SchedulingConfig` (`core.shared.config`) enables scheduling once. Scanner: `VirusScanService` (`ClamdVirusScanService`; `app.scan.type=none` in dev). CSV export expiry is `app.export.file-expiry-hours` (24). PDF: Apache PDFBox 3.0.3 + embedded IPAex Gothic. MIME detection: Tika `tika-core`.
- Audit columns (`created_*`/`updated_*`) are filled by the `MetaObjectHandler` MyBatis interceptor; services do not set them. Shared code: `UserContext.getUserId()`, `Result`/`PageResult`, `BusinessException`.
- File storage is Local (default) and S3 (`LocalFileStorageService` / `S3FileStorageService`); there is no MinIO-specific class.
- There are no encrypted business columns, no SMS, no department/employee tables.
- Do not introduce fixed example identities, table counts, or undocumented defaults. Derive names, tables, endpoints, seed data, and generated paths from the sources above.

## Test conventions

- **Decision (2026-10-21):** UT case lists live in the detailed design's `§5.1` and ids are `UT-<FEATURE>-NNN` (3 digits). `<FEATURE>` is the abbreviation in `spec-test-rule.md` §5: user=USR, customer=CUS, product=PRD, order=ORD, approval=APR, attachment=FIL, report=RPT (e.g. `UT-ORD-001`). All 7 detailed designs now follow this (lists in §5.1, ids `UT-USR/CUS/PRD/ORD/APR/FIL/RPT-NNN`).
- **Decision:** Mapper XML uses `resultMap` first (underscore mapping stays enabled). **Decision:** file storage defaults to `local` (`FILE_STORAGE_TYPE`, `S3_*` only when `s3`). **Decision:** frontend tests run on `jsdom` (pin the version). Containerized deployment (`spec-scaffold-deploy`) is on hold.
- Review status values in IT specs: 草案 / レビュー中 / 承認済み (from the DDMSAA templates).
- Test reports read JUnit XML (`spec-test-rule.md` §7).
